In-App Visual QA Tool

Pin a bug report exactly where you see it — a drop-in, browser-based QA tool that replaced hand-maintained bug spreadsheets.

Built during the same engagement as my K–12 game work — I created this tool to fix the QA workflow of the very games I was building. Anonymized here like the games; the engineering is the story.

Overview

A browser-based QA tool that lets testers and reviewers click any element on a live build to pin a bug or comment exactly where they see it. Every pin carries a structured, exportable bug report backed by a shared database — and the whole tool is one self-contained folder that drops into any web project.

The problem

QA for our games lived in a hand-maintained spreadsheet. Every bug row had to be cross-referenced back to the actual spot in the running game — slow, error-prone, and the context ("which screen? which button?") kept getting lost between tester and developer. I was on the receiving end of those bug reports, so I felt the friction directly.

The approach

Move bug reporting into the running product. Toggle comment mode, click the broken thing, fill a structured form — the pin captures the element's CSS selector, coordinates, and the active screen automatically. The bug sheet everyone used to maintain by hand becomes a one-click CSV export.

How it works

01

Pin it where you see it

Click any UI element to drop a numbered pin. Each pin captures the CSS selector, x/y position, and auto-detected screen — anyone can jump straight to the issue. A collapsible sidebar lists pins per screen with status filters.

02

Role-aware reporting

Three password-gated roles. QA gets a proper bug form (description, repro steps, expected vs actual); stakeholders get a lightweight comment box; the owner reviews everything. Threaded replies turn each pin into a conversation.

03

Dual-status workflow

QA owns Pass/Fail (built for the retest loop); the developer owns Open → In Progress → Resolved / Won't Fix (reason required). Permissions are enforced in the UI and on the server — mirroring a real bug-tracking pipeline.

The engineering

  • Frontend is vanilla JavaScript ES modules + CSS — no framework, no build step; clean module separation (data layer, popup UI, sidebar, CSV export, mode controller), each independently testable
  • Backend on Supabase: PostgreSQL with Row-Level Security, plus a Deno Edge Function as the security gatekeeper — all privileged mutations route through password-validated, server-side checks with column whitelisting; secrets never touch the client
  • One-click CSV "bug sheet" — role-scoped columns, properly escaped, UTF-8 BOM so it opens cleanly in Excel/Sheets, with a timestamped project-named filename
  • Reusable by design: one folder, namespaced per app, so many projects share one backend without collisions — integrating a new project is config-only, ~20 minutes with the setup guide
  • Production-safe: activates only with ?qa=true in the URL — completely inert (zero UI, zero cost) for real users, fully removable by deleting one folder and one script tag

What it changed

  • Bug reports moved from a manual spreadsheet into the product itself — pinned in context, structured, and screen-tagged
  • The tester's documentation kept its familiar spreadsheet form — now generated on demand instead of maintained by hand
  • QA, developer, and stakeholders collaborate on the same pins in real time, across sessions and devices
  • Adopted across multiple projects from a single shared backend
